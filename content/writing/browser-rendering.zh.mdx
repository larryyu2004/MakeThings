# 浏览器如何把页面变成像素

浏览器不会直接把 HTML 文件画到屏幕上。它需要解析资源、计算样式、排列盒子、生成绘制操作，再展示结果。原笔记把过程列成八个固定阶段，作为入门模型很有帮助；但真实引擎可能以不同方式调度、跳过、合并或重复这些工作。这里保留这个模型，同时区分通用概念与实现细节。

## 从 HTML、CSS 到布局盒子

解析 HTML 会建立文档树。CSS 被解析为参与样式计算的规则。样式表不一定像阻塞解析的经典脚本那样暂停 HTML 解析，但它可能延迟页面渲染，也可能延迟依赖样式的脚本。没有 `async` 或 `defer` 的经典脚本会在获取和执行期间暂停 HTML 解析；`defer`、`async` 与模块脚本会改变调度方式。

```text
HTML + CSS → DOM + 样式规则 → 计算后样式 → 布局盒子
```

浏览器根据选择器和继承关系求出元素的计算后样式。随后布局阶段计算宽、高和位置等几何信息。布局结果并非 DOM 的逐项复制：`display: none` 的元素不生成布局盒子，而生成内容与匿名盒子可能出现于布局结构中。

<Key>“解析”“样式计算”和“布局”代表不同的工作。首帧完成之后，页面仍可能多次重新计算样式或布局。</Key>

## 绘制与合成

绘制阶段记录背景、文字、边框、阴影等内容所需的视觉操作。浏览器可能把这些操作组织成图层，把表面分为图块，将其栅格化为像素，最后合成。图层和图块是有用的概念，但具体进程、线程分工取决于引擎、设备和页面。

简化后的单帧流程如下：

```text
DOM 或样式发生变化
  → 必要时计算样式
  → 几何信息变化时进行布局
  → 像素变化时绘制或栅格化
  → 合成并显示
```

改变元素宽度通常需要重新布局，随后还会有其他视觉工作。改变颜色通常需要重新绘制，但无需布局。若元素已准备为合成图层，`transform` 或 `opacity` 动画有时可以主要由合成阶段处理，所以它们常是合适的动画属性。**只由合成器处理是一种优化，而非普遍保证**：图层建立、滤镜、效果及周边变化仍可能带来额外工作。

## 为什么长时间运行的 JavaScript 会产生影响

JavaScript、样式计算、布局和大部分绘制准备工作都会争用页面主线程的时间。一个长任务会延迟事件处理，也会延迟新画面所需的工作。使用 `transform` 移动元素可以减少布局开销，但不能让主线程阻塞对所有动画和交互都失去影响。

对于交互页面，实际做法是测量正在发生的工作：记录性能轨迹，查找长任务、重复布局、大面积绘制和过多图层，再逐个处理原因。需要动画时优先考虑 `transform` 与 `opacity`，但仍要在目标设备上确认效果。

## 我的收获

渲染流程最适合作为排查问题的地图。先问：**这次变化需要浏览器做哪类工作？**再用浏览器工具验证。这样比永久地把每个 CSS 属性划分为“快”或“慢”更可靠。
