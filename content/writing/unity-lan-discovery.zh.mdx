# 在局域网中发现 Unity 主机

本地多人游戏有两项不同的工作：**发现主机**与**连接主机**。发现只告诉客户端可以尝试连接哪里；真正建立会话的是传输层。原笔记把这两步写在一起，容易让人误以为收到广播就等于连接成功。界面和代码都应该分别表示这两种状态。

## 发现流程

主机先启动传输层监听，再定期向局域网发送少量 UDP 发现消息。客户端在约定端口监听、验证消息并显示候选主机。玩家选择主机后，客户端才让 Unity Transport 发起连接。

这里讨论的是自定义发现协议。Unity 旧版 UNet 的 `NetworkDiscovery` 组件已属于旧方案，不能误认为当前 Netcode for GameObjects 自带同样的发现功能。

```text
主机：启动监听 → 发送发现消息
客户端：接收 → 验证 → 显示候选主机 → 发起连接
传输层：完成连接握手后才算已连接
```

<Key>收到发现消息只能证明这个数据包到达了客户端，不能证明游戏端口可用，也不能证明传输层已经连接成功。</Key>

发现消息可以包含协议版本、会话标识、游戏端口和简短名称，不应包含凭据。客户端应忽略格式错误、版本不兼容、来自自身以及重复会话的消息。候选主机还需要过期时间，避免主机离开后仍留在列表中。

## 选择地址

设备可能同时拥有 Wi-Fi、蜂窝网络、VPN、虚拟网卡和回环接口。直接使用 API 返回的第一个 IPv4 地址并不可靠。游戏连接所用的地址必须属于能到达对端的网络接口。开热点的手机和加入 Wi-Fi 的手机，其可用接口也可能不同。

如果条件允许，让接收套接字提供发送方地址，广播内容只公布游戏端口。若主机必须公布地址，就要根据当前网络接口选择，并在真实设备上验证。广播不可用时，保留手动输入 IP 的入口。

## 线程与生命周期

接收套接字不能阻塞 Unity 主线程。后台任务完成数据验证后，再把结果交给主线程更新 GameObject 或界面。离开发现界面、主机停止或应用退出时，应停止收发任务。即使发生取消或接收错误，也必须释放套接字。

```csharp
// 概念性边界：套接字任务在 Unity 主线程之外运行。
while (!cancellationToken.IsCancellationRequested)
{
    var packet = await ReceiveDiscoveryPacketAsync(cancellationToken);
    if (TryReadAdvertisement(packet, out var host))
        mainThreadQueue.Enqueue(() => ShowOrRefreshHost(host));
}
```

## 热点与平台限制

UDP 广播可以用于共享局域网，但热点路由、客户端隔离、系统权限和防火墙规则因设备而异。不能把某个热点网段写死为通用规则。在 iOS 上，本地网络访问可能触发权限提示，应用需要说明访问目的。设备验证应覆盖 Wi-Fi、手机热点下的双向主机角色、应用切换前后台、主机离开及拒绝本地网络权限。

发现失败时，界面应显示**未找到主机**，而不是**连接失败**。若已经发现主机但传输层无法连接，则应报告另一种失败，并提供重试或手动地址入口。

## 我的收获

可靠的设计可以用一个小状态机表达：搜索中、发现主机、连接中、已连接和失败。每次状态转换都有自己的证据与超时。相比单一的“多人游戏已就绪”标记，这种模型更容易调试，也更容易让玩家理解。
