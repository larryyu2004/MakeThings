# 从浏览器轨迹识别布局与绘制

渲染流程图可以帮助提出假设，却不能告诉我们某个页面实际做了多少工作。旧版浏览器笔记把解析、样式、布局、绘制、图块和栅格化列成固定顺序。真实浏览器可能跳过、重复或重新组织其中的步骤。我更愿意把这些阶段当作查看性能轨迹时的问题清单。

## 哪种输入发生了变化

如果变化影响元素的几何尺寸，浏览器可能需要重新布局，随后还有视觉处理。改变颜色通常需要绘制，而不用重新计算几何信息。元素准备妥当后，`transform` 有时可以在合成阶段处理，但这取决于页面与引擎。不能永久地给某个 CSS 属性贴上“快”或“慢”的标签。

JavaScript 若交替写入改变布局的属性，又读取必须立即更新的几何尺寸，也可能造成反复布局。性能轨迹会显示脚本、样式计算、布局、绘制与画面显示的实际顺序和耗时。这比笼统的属性分类更有用。

## 一个测量循环

在浏览器 Performance 面板录制有代表性的交互，找到输入事件和下一次可见画面。检查长任务、重复布局、大面积绘制及意外创建的图层。一次只调整一个原因，再次录制，并在重要的设备上比较。

<Key>流程图说明页面可能进行哪些工作；性能轨迹说明这个页面实际做了什么。</Key>

这样写渲染文章更有实践价值：目标不是宣称所有动画都应使用某个属性，而是判断实测的帧能否满足交互需要。
