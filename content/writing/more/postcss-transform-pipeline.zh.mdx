# 将 PostCSS 理解为 CSS 转换流水线

旧的独立 PostCSS 文件是空的。因此这篇是结合前端工程笔记写成的概念入门，不表示某个具体项目已经采用 PostCSS。它的核心思路是：先把 CSS 解析成结构，由插件修改，再输出 CSS。实际发生什么变化，取决于项目配置了哪些插件。

## 工具与插件的分工

PostCSS 本身不是一种新的 CSS 语法，也不是一个自动开启的兼容性开关。解析器生成抽象语法树；插件检查或转换这棵树；输出步骤再生成 CSS。插件可以添加浏览器前缀、检查样式规则，或执行其他明确的转换。仅安装 PostCSS 并不保证这些效果。

假设样式表用了某项功能，而产品支持的某些浏览器需要兼容转换。团队应先声明浏览器目标，再选择合适插件，最后比较生成 CSS 与预期结果。对旧环境有用的转换，在较新目标下可能已经没有必要。CSS 输出的改变也可能影响视觉行为，因此构建检查之外还需要页面检查。

## 它在构建流程中的位置

通常由构建工具读取样式表，调用配置好插件的 PostCSS 处理器，并把结果写入可部署资源。配置文件与插件顺序取决于具体工具。页面样式异常时，可以依次检查原始 CSS、插件配置、生成 CSS 和浏览器计算后的样式。这样才能分清问题发生在编写、转换，还是资源送达后的级联规则。

更实用的表达是说明每个插件产生什么可观察的输出，而不是把“使用 PostCSS”本身当成产品特性。只有某项转换或检查服务于明确的浏览器目标和设计要求，这条流水线才真正有价值。
